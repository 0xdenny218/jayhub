# jayhub 站点交付手册

**交付对象**　甲方技术运维及运营负责人

**交付版本**　基于 New API `v1.0.0-rc.51`，本次交付源码由运营提供的 Git 提交号标识。[查看本次交付源码](https://github.com/0xdenny218/jayhub/tree/main)

## 一、接收项目与上游账号

请联系供货方运营确认本次交付版本和已开通的模型。源码可从 [jayhub 代码仓库](https://github.com/0xdenny218/jayhub) 通过 HTTPS 克隆。若运营为甲方单独提供私有仓库，请提供 GitHub 用户名，用受邀账号接受邀请后使用运营提供的仓库地址。

甲方独立运行本站。终端用户向甲方注册、充值并申请 API 密钥。用户的模型请求经过甲方站点，使用供货方分配给甲方的上游 API Key 转发到供货方平台，再由供货方转发到对应的官方模型渠道。

| 接收或准备的内容 | 由谁提供 | 用途 |
| --- | --- | --- |
| 代码仓库地址和交付版本（含首页、登录页和 Docker Compose） | 供货方运营 | 甲方在自己的服务器构建和运行站点 |
| 供货方网关 Base URL、甲方专属上游 API Key、已开通的模型 ID 和协议 | 供货方另行交接，密钥通过私密渠道传递 | 甲方管理员在后台配置上游渠道 |
| 服务器、域名、HTTPS 证书和备份位置 | 甲方 | 对外提供服务并保管数据 |
| 站点管理员、零售价、用户额度及退款规则 | 甲方 | 管理终端用户和本站账单 |

**两套账单独立结算。** 甲方依据本站的用量记录和零售价向终端用户收费、处理退款。供货方依据供货方平台上甲方账户的账单向甲方收费。甲方向终端用户退款时，上游费用按双方约定另行处理。

## 二、部署三个服务

以下以一台 Linux 服务器和同机 HTTPS 反向代理为例，命令在 Bash 中执行。运维账号需能使用 Git、Docker Engine、Docker Compose 插件、OpenSSL 和 curl，并有权写入部署目录。首次构建需要访问基础镜像仓库、Go 模块源和前端依赖源。请预留本机 `127.0.0.1:3000`。

### 1. 取得本次交付源码

以下命令适用于新部署。已运行旧版的实例请先按[单机部署与运维中的升级说明](./DEPLOYMENT.zh-CN.md)保留原项目名、密钥和数据卷。

```bash
git clone https://github.com/0xdenny218/jayhub.git /opt/jayhub
cd /opt/jayhub
read -rp '输入运营提供的交付提交号：' delivery_commit
git checkout --detach "${delivery_commit:?请填写本次交付提交号}"
```

部署入口是 **`delivery/compose.yaml`**，它从交付源码构建带有定制页面的应用。根目录的 `docker-compose.yml` 使用上游镜像。甲方域名、证书私钥、数据库备份和真实密钥请保存在源码目录之外。[交付版 Compose 配置](https://github.com/0xdenny218/jayhub/blob/main/delivery/compose.yaml)

### 2. 生成部署密钥

将第一行示例域名换成甲方浏览器实际使用的 HTTPS 地址，可带端口，省略末尾斜杠。首次部署执行一次。下面的命令会拒绝覆盖已有配置文件。

```bash
SITE_ORIGIN='https://gateway.example.com'
(
  set -euC
  umask 077
  mkdir -p "$HOME/.config/jayhub"
  {
    printf 'SITE_ORIGIN=%s\n' "$SITE_ORIGIN"
    echo 'COMPOSE_PROJECT_NAME=jayhub'
    for key in POSTGRES_PASSWORD REDIS_PASSWORD SESSION_SECRET CRYPTO_SECRET; do
      value=$(openssl rand -hex 32)
      printf '%s=%s\n' "$key" "$value"
    done
  } > "$HOME/.config/jayhub/deploy.env"
)
```

请将 `deploy.env` 单独备份到甲方控制的密钥存储。升级和恢复时使用原文件。上游 API Key 在第四节的管理页面录入。

### 3. 构建与检查

```bash
cd /opt/jayhub
dc() {
  docker compose --env-file "$HOME/.config/jayhub/deploy.env" \
    -f /opt/jayhub/delivery/compose.yaml "$@"
}
dc config --quiet
dc up -d --build
dc ps
curl -fsS http://127.0.0.1:3000/api/status
```

等待 `app`、`postgres`、`redis` 全部显示 `healthy` 后再初始化。状态接口应返回 `"success":true`，新站的 `data.system_name` 为 `jayhub`。应用端口仅绑定本机，PostgreSQL 和 Redis 只在 Compose 网络内提供服务。后文的 `dc` 指上面的函数，重新打开终端时需再次定义。

## 三、通过 HTTPS 创建管理员

1. 将甲方域名解析到服务器，在宿主机反向代理上配置该域名的 HTTPS 证书，将请求转发到 `http://127.0.0.1:3000`。保留原始 Host，并向应用传递 `X-Forwarded-Proto: https`。若使用 Nginx，在代理 API 的位置配置 `proxy_buffering off;`，以便流式响应逐段到达客户端。
2. 初始化前先将域名访问限制为运维人员。使用浏览器打开与 `SITE_ORIGIN` 完全一致的地址，首次访问会进入初始化向导。
3. 确认向导识别到 PostgreSQL，设置甲方管理员用户名和密码，选择 **「对外运营」**，完成初始化。由甲方保管管理员凭据。
4. 回到首页后登录控制台，刷新一次页面以验证会话。在「系统设置 → 站点 → 系统信息」填写甲方对外地址、核对站名与 Logo。首页应显示模型目录；此时尚未接入渠道，模型数量可以为 0。

## 四、配置上游渠道与本站零售价

| 控制台位置 | 甲方操作 |
| --- | --- |
| 渠道 | 新建渠道，按供货方提供的协议选择渠道类型，填入供货方网关地址和**甲方专属上游 Key**。勾选双方约定的模型 ID，设置渠道分组并启用。选择已开通模型执行一次渠道测试。 |
| 系统设置 → 计费 → 模型定价、分组定价 | 为对外提供的模型设置本站零售价，核对计费单位和分组倍率，保存。文本、图片和视频应分别核对实际使用的计价方式。 |
| 用户、API 密钥 | 创建一个普通验收账号并分配足够的测试额度；以该账号登录，签发**本站用户 Key**。确认令牌分组可使用上述渠道，并允许访问测试模型。 |
| 使用日志 | 完成一次终端调用后，通过时间、模型、令牌或请求 ID 查找本站记录，核对实际用量和扣费。 |

**两个 Base URL 填在不同位置。** 例如，供货方提供的普通 OpenAI 兼容接口是 `https://upstream.example.com/v1/chat/completions`，则渠道地址填写 `https://upstream.example.com`，网关会拼接请求路径。终端用户在 OpenAI 兼容客户端填写的地址则是 **`https://甲方域名/v1`**，并使用本站用户 Key。其他协议按对应渠道说明填写。

## 五、上线验收

先用普通验收账号做一次小额请求。以下示例适用于已开通 Chat Completions 的文本模型。将命令中的域名和 `YOUR_ENABLED_CHAT_MODEL` 换成实际值；提示输入密钥时使用**本站用户 Key**。

```bash
SITE_ORIGIN='https://gateway.example.com'
read -rsp '输入本站验收用户的 API Key：' SITE_USER_KEY
printf '\n'
curl -sS --fail-with-body "$SITE_ORIGIN/v1/models" \
  -H "Authorization: Bearer $SITE_USER_KEY"
curl -sS --fail-with-body "$SITE_ORIGIN/v1/chat/completions" \
  -H "Authorization: Bearer $SITE_USER_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"model":"YOUR_ENABLED_CHAT_MODEL","messages":[{"role":"user","content":"请回复 OK"}]}'
unset SITE_USER_KEY
```

| 验收项 | 通过条件 | 验证情况 |
| --- | --- | --- |
| 部署与管理员 | 三个服务健康，HTTPS 首页可访问，管理员可完成初始化并登录。保留卷重建容器后，同一管理员仍可登录。 | 交付前已在 Mac Docker Desktop 的独立环境通过；甲方在目标域名复核。 |
| 文本与账单 | 模型列表包含约定模型，聊天请求返回内容。甲方在本站查到验收用户的扣费，供货方在自己的平台查到甲方账户的用量。双方按时间、模型及可用请求标识核对，各自按约定价格结算。 | 接入真实上游 Key 后由双方联验。 |
| 图片、视频（按开通范围） | 图片生成后可从外网获取结果。异步任务需记录任务 ID，轮询至完成并下载产物，同时核对本站与上游记录。需要网关生成产物链接时，确认对外地址使用甲方可访问的 HTTPS 域名。 | 分别选用一个已开通的图片或视频模型联验。 |

记录验收日期、交付版本、测试模型、请求或任务 ID 和验收人。渠道测试或模型列表查询通过后，仍需完成实际调用和账单核对，再向终端用户分发令牌。

## 六、运维与数据保管

| 场景 | 操作 |
| --- | --- |
| 查看状态或启动异常 | `dc ps`；按服务检查 `dc logs --tail=100 app postgres redis`。 |
| 重启应用、停机维护 | `dc restart app`；整站暂停用 `dc stop`，恢复用 `dc start`。保留三个数据卷，`down -v` 会删除账号、账单等持久化数据。 |
| 模型不可用或额度不足 | 核对上游开通的模型 ID、渠道启用状态、令牌分组、本站定价及用户额度；再由供货方检查上游账号额度。 |
| 备份与恢复 | `pg_data` 保存账号和账单，`app_data` 保存应用文件及日志，`redis_data` 保存 Redis 持久化数据。备份三个卷和部署密钥，保留异机副本，在独立环境验证恢复。 |
| 升级 | 记录当前源码提交并备份数据及配置，切至双方确认的新版本，再执行 `dc up -d --build`。复验登录、模型调用和账单。若版本包含数据库迁移，回滚时使用匹配版本的数据库备份。 |

数据库可通过 `pg_dump` 导出。更多备份命令及运维说明见[单机部署与运维](https://github.com/0xdenny218/jayhub/blob/main/delivery/DEPLOYMENT.zh-CN.md)。源码随附 [LICENSE](https://github.com/0xdenny218/jayhub/blob/main/LICENSE) 和 [NOTICE](https://github.com/0xdenny218/jayhub/blob/main/NOTICE)，站点页脚保留 New API 署名。
